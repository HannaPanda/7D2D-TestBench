# Languages

The tool speaks the languages 7 Days to Die itself ships, and it uses the same
names: `english`, `german`, `spanish`, `french`, `italian`, `japanese`, `koreana`,
`polish`, `brazilian`, `russian`, `turkish`, `schinese`, `tchinese`. Those are
exactly the columns of the game's `Data/Config/Localization.csv`. Anybody who has
ever translated something in there knows immediately which file to open.

## Where the language comes from

In this order:

1. `--lang <language>` on the call
2. `language` in `testbench.json` (in the window, the switch in the top right)
3. the system language
4. English

Number 3 accepts relatives too: `de-AT` finds German, `pt-PT` finds the Brazilian
catalog, `zh-Hans-CN` finds simplified Chinese. A language there is no catalog for
leads to English, not to empty lines.

An unknown value is not an error. A typo in the configuration must not prevent a
test run, so it ends up at English.

## How the catalogs are loaded

Every catalog is a flat JSON file, key to text:

```json
{
  "status.ok": "OK",
  "cli.run.counters": "ERR {0}  EXC {1}  XML {2}  ignored {3} of {4} lines"
}
```

They exist twice: **embedded** in `Testbench.Core.dll`, so the tool knows every
language even without side files, and as **files** in `lang\` next to the exe. The
file wins, key by key. That is how a bad translation is corrected without a rebuild:

```
lang\german.json      only the keys you want to change
```

Everything missing there still comes from the built-in catalog, then from the
English one, and last of all the key itself appears. That is on purpose:
`gui.startRun` in a button is an error message, an empty area is not.

A language of your own is a new file: `lang\czech.json`, and it is in the menu.
Missing keys are named by

```bash
tb lang czech --check
```

## Rules for changes to the code

1. **No new text without a key.** Everything a human reads goes through
   `Loc.T(...)`, or `{local:Tr key}` in XAML.
2. **A new key belongs in *every* shipped catalog.** The test
   `Every_shipped_catalog_is_complete` enforces that. A language that has no file
   yet is not meant by this: it is missing entirely and falls back to English, which
   is honest. Half-translated catalogs do not exist here.
3. **Placeholders stay the same.** `Placeholders_match_english` compares the `{0}`,
   `{1}` of every text against the English one. A translation that loses a `{0}`
   loses the file name or the PID it was about.
4. **Do not touch the German status labels.** `status.modNotLoaded` and the others
   are literally the output of the old PowerShell scripts, so that old and new
   reports stay comparable.
   `The_german_status_labels_are_the_ones_the_old_scripts_printed` holds that down.
5. **Verbs and options are not translated.** `tb run --mod`, `--visual ok`,
   `headless`, `gui`: that is the contract scripts and agents hang on. A translated
   flag would be a different program. What gets translated is the description next
   to it.
6. **`--json` stays machine readable.** The prefixes `WARN:` and `ERROR:` in
   `messages` are English regardless of the language. The texts inside them are
   translated, the field names and `statusCode` are not.
7. **The German catalog does without umlauts** (`ae`, `oe`, `ue`, `ss`). Its texts
   run through Windows consoles with code pages that date back to the nineties; this
   is a deliberate precaution and not sloppiness. Other languages use their script
   normally, the console is switched to UTF-8.

## Checking

```bash
tb lang
```

Shows every available language, which one is active, which one the system language
would be, and how many keys a file is missing.

```bash
tb lang german --check
```

Names every missing key one by one. Without a language it checks the active one.
