# Sprachen

Das Werkzeug spricht die Sprachen, die 7 Days to Die selbst mitbringt, und es
benutzt dieselben Namen: `english`, `german`, `spanish`, `french`, `italian`,
`japanese`, `koreana`, `polish`, `brazilian`, `russian`, `turkish`, `schinese`,
`tchinese`. Das sind genau die Spalten der `Data/Config/Localization.csv` des
Spiels. Wer dort schon einmal etwas übersetzt hat, weiß sofort, welche Datei er
öffnen muss.

## Woher die Sprache kommt

In dieser Reihenfolge:

1. `--lang <sprache>` beim Aufruf
2. `language` in der `testbench.json` (im Fenster der Umschalter oben rechts)
3. die Systemsprache
4. Englisch

Punkt 3 nimmt auch Verwandte: `de-AT` findet Deutsch, `pt-PT` findet den
brasilianischen Katalog, `zh-Hans-CN` das vereinfachte Chinesisch. Eine Sprache,
für die es keinen Katalog gibt, führt zu Englisch und nicht zu leeren Zeilen.

Ein unbekannter Wert ist kein Fehler. Ein Tippfehler in der Konfiguration darf
keinen Testlauf verhindern, deshalb landet er bei Englisch.

## Wie die Kataloge geladen werden

Jeder Katalog ist eine flache JSON-Datei, Schlüssel auf Text:

```json
{
  "status.ok": "OK",
  "cli.run.counters": "ERR {0}  EXC {1}  XML {2}  ignored {3} of {4} lines"
}
```

Sie liegen doppelt vor: **eingebettet** in `Testbench.Core.dll`, damit das
Werkzeug auch ohne Beidateien alle Sprachen kann, und als **Dateien** in `lang\`
neben der Exe. Die Datei gewinnt, Schlüssel für Schlüssel. Damit wird eine
schlechte Übersetzung ohne Neubau korrigiert:

```
lang\german.json      nur die Schlüssel, die man ändern will
```

Alles, was dort fehlt, kommt weiter aus dem eingebauten Katalog, dann aus dem
englischen, und zuletzt erscheint der Schlüssel selbst. Das ist Absicht:
`gui.startRun` in einem Knopf ist eine Fehlermeldung, eine leere Fläche nicht.

Eine eigene Sprache ist eine neue Datei: `lang\czech.json`, und sie steht im
Menü. Fehlende Schlüssel nennt

```bash
tb lang czech --check
```

## Regeln für Änderungen am Code

1. **Kein neuer Text ohne Schlüssel.** Alles, was ein Mensch liest, geht durch
   `Loc.T(...)` beziehungsweise `{local:Tr key}` im XAML.
2. **Ein neuer Schlüssel gehört in *alle* ausgelieferten Kataloge.** Der Test
   `Every_shipped_catalog_is_complete` erzwingt das. Eine Sprache, die noch keine
   Datei hat, ist damit nicht gemeint: die fehlt ganz und fällt auf Englisch
   zurück, was ehrlich ist. Halb übersetzte Kataloge gibt es nicht.
3. **Platzhalter bleiben gleich.** `Placeholders_match_english` vergleicht die
   `{0}`, `{1}` jedes Textes mit dem englischen. Eine Übersetzung, die ein `{0}`
   verliert, verliert den Dateinamen oder die PID, um die es ging.
4. **Deutsche Statuslabels nicht anfassen.** `status.modNotLoaded` und die anderen
   sind wörtlich die Ausgaben der alten PowerShell-Skripte, damit alte und neue
   Reports vergleichbar bleiben. `The_german_status_labels_are_the_ones_the_old_scripts_printed`
   hält das fest.
5. **Verben und Optionen werden nicht übersetzt.** `tb run --mod`, `--visual ok`,
   `headless`, `gui`: das ist der Kontrakt, an dem Skripte und Agenten hängen. Ein
   übersetztes Flag wäre ein anderes Programm. Übersetzt werden die
   Beschreibungen daneben.
6. **`--json` bleibt maschinenlesbar.** Die Präfixe `WARN:` und `ERROR:` in
   `messages` sind englisch, unabhängig von der Sprache. Die Texte darin sind
   übersetzt, die Feldnamen und `statusCode` nicht.
7. **Der deutsche Katalog verzichtet auf Umlaute** (`ae`, `oe`, `ue`, `ss`). Die
   Texte laufen durch Windows-Konsolen mit Codepages, die noch aus den Neunzigern
   stammen; das hier ist eine bewusste Vorsichtsmaßnahme und keine Nachlässigkeit.
   Andere Sprachen benutzen ihre Schrift normal, die Konsole ist auf UTF-8
   gestellt.

## Prüfen

```bash
tb lang
```

Zeigt jede vorhandene Sprache, welche aktiv ist, welche die Systemsprache wäre,
und wie viele Schlüssel einer Datei fehlen.

```bash
tb lang german --check
```

Nennt jeden fehlenden Schlüssel einzeln. Ohne Sprachangabe prüft es die aktive.
